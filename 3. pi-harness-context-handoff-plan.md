# Context handoff on the Pi harness — build plan

Pattern per specs 1 and 2: one persistent base session, short-lived working
sessions, base kept compact by accumulated handoffs. Target: Pi harness + local
model, replacing Claude CLI + tmux.

Status markers: **[V]** verified, with source. **[?]** unknown, unverified.

---

## READ FIRST — this project starts with research and spikes, not code

For the agent building this as a new project. Non-negotiable ordering.

**Nothing in this document is a design to implement as written.** It is a
requirements + constraints record with the unknowns marked. Several `[?]` items
determine the architecture and are not yet answered.

**Do this before writing any production code:**

1. **Survey existing solutions and packages before building anything custom.**
   For every component in the tool inventory, ask first whether something already
   does it. Prioritize this analysis — a component that a maintained package
   already provides should not be hand-written.
2. **Run the spikes** in Phase 1 stages 1a–1c and Phase 2 stage 2a–2b. Each is
   cheap and each closes an unknown that changes the design.
3. **Read the actual docs and source** of every external dependency before
   designing against it. Not memory, not recollection, not this document's
   summaries.
4. **Record spike results back into this document** (or its successor) with a
   `[V]` marker and the source, so the next reader inherits fact rather than
   guess.

**Anti-pattern this project already paid for:** substituting a remembered or
invented mechanism for the documented one, then building on it. That cost a full
day of debugging in the Claude-CLI predecessor, and the resulting defect was
invisible because a large fake-driven test suite stayed green throughout. Spike
the mechanism, then build.

**Do not skip the package/framework survey because the custom path looks
straightforward.** See "Frameworks and packages to evaluate" below — it is a
required research task, not an optional consideration.

## Constraint that drives the design

- Hard context ceiling, not a cost curve. Design budget: **120–240k**, the range
  common to modern gemma4-class models. Exact figure is deployment-dependent
  (quant, KV cache type, slot count, VRAM across GPUs) — treat as configurable,
  not constant.
- **[V]** Fresh-process-per-turn re-prefills the whole growing context →
  O(n²) prefill. (`Unharness/HANDOFF-pi-rpc-mode-integration-plan.md`)
- Goal: working sessions stay small; base carries continuity; no per-rotation
  re-prefill.
- Ceiling is a config value, not a literal. Loop must read it and act on
  remaining budget.
- **Stated (architect):** gemma4 sliding input window is 1k → prefill advances
  1k tokens at a time → session preambles are expensive to (re)generate.
  Consequence: never re-prefill a preamble that can be restored instead.

## Phase 1 — KV cache session store (separate repo)

**Scope of phase 1 is this and nothing else.** Standalone git repo; the
context-handoff project depends on it as an external dependency.

Proposed repo name: `llm-kv-cache-session-store` (confirm before creating).

Purpose: save, restore, and duplicate a session's KV cache to and from disk so
sessions can be branched and resumed without holding multiple caches in VRAM.
Backend-agnostic by construction.

**Hard invariant: exactly one KV cache resident in VRAM at any time.** Multiple
resident caches divide the context budget; one resident cache maximizes it. Disk
read/write latency is accepted in exchange.

Prefill cost, not token cost, is the thing eliminated. Restoring a cache
replaces re-prefilling.

### Interface — generic, backend-independent

- `save_session_kv_cache_to_disk(session_id)`
- `load_session_kv_cache_into_vram(session_id)`
- `duplicate_session_kv_cache_for_branch(parent_session_id, new_session_id)`
- `evict_resident_session_kv_cache()`
- `list_saved_session_kv_caches()`
- `describe_backend_cache_capabilities()` — what this backend actually supports,
  so callers can degrade rather than fail

Rules:

- Interface mentions no backend, no server, no wire format. Same rule as the
  existing `interfaces/` package, which has a test asserting it names neither
  harness nor terminal.
- One adapter per backend behind the interface. Adapters are independently
  testable against a live server; the interface is testable against a fake.
- Adapters declare capabilities rather than pretending uniformity. A backend that
  cannot duplicate into a different sequence must say so.

### Store responsibilities

- Cache artifact + its serving-parameter fingerprint, stored together.
- Invalidation on mismatch: model, quant, KV cache type, context size, chat
  template. A cache restored under different serving params is invalid.
- Torn-write recovery; atomic publish of a saved artifact.
- Cache↔transcript pairing is **the caller's** concern, not the store's — the
  store keys by session id and stays out of transcript formats. (The harness owns
  transcripts; see the tool inventory.)
- CLI over the same interface, for spikes and manual recovery without the app.

### Measure and publish in the repo README

- save time, load time, on-disk size per 10k tokens, at the configured ceiling
- per backend adapter
- these numbers set the practical rotation frequency

## Pi RPC surface

Source: `Unharness/HANDOFF-pi-rpc-mode-integration-plan.md`, quoting pi
`docs/rpc.md` @ 0.74.2. Not run locally — pi is not installed on this host.

- **[V]** `pi --mode rpc`; process persists; commands = JSONL on stdin, one per
  line.
- **[V]** Framing strict LF-only. Split on `\n`, strip trailing `\r`. Do not use
  a reader that also splits U+2028/U+2029 (valid inside JSON strings).
- **[V]** Commands: `prompt`, `steer`, `follow_up`, `abort`, `new_session`
  (`parentSession` optional), `get_state`, `get_messages`, `set_model`,
  `cycle_model`. Optional `id` echoed on response.
- **[V]** `prompt` while streaming requires `streamingBehavior: "steer"|"followUp"`
  or errors.
- **[V]** Events: `message_start/update/end`, `tool_execution_start/update/end`,
  `turn_start/end`, `agent_start/end`, session header. Interleaved with
  `{"type":"response"}` command acks — normalizer must skip those.
- **[V]** `get_state` → `sessionId`, `sessionFile`, `isStreaming`, `messageCount`.
- **[V]** Sessions persist as jsonl under `--session-dir`.
- **[V]** `abort` cancels upstream generation and preserves session. llama.cpp
  `is_processing` false 0.03s after abort, mid-generation. No OS-kill needed.
- **[V]** pi is always full-auto; permission modes ignored. Isolation = VM
  (libvirt `claude-sandbox`; host at `192.168.122.1`).
- **[V]** `before_provider_request` extension hook rewrites outgoing payload.

## Backend — selection open

llama.cpp is the incumbent, **not** the decision. It may not meet the cache
requirement. Evaluate before committing.

Candidates to research (capabilities all **[?]** — do not assume):

- llama.cpp / `llama-server`
- vLLM
- SGLang
- LMCache (KV layer rather than a server; may pair with one of the above)
- TensorRT-LLM
- ExLlamaV2 / TabbyAPI

Selection criteria, in priority order:

1. Can KV cache be exported and re-imported at all
2. Can a saved cache be restored into a **different** session/sequence — the
   duplication that makes branching possible
3. Artifact portability: survives process restart; usable cross-process
4. Which serving params must match on restore (model, quant, KV type, context
   size, template)
5. Single-resident-cache operation without forced multi-slot VRAM allocation
6. Save/load throughput and on-disk size per 10k tokens
7. Sliding-window model support
8. Tool-calling fidelity — no control-token leakage into the response
9. OpenAI-compat completion surface (needed for the base-session role)

Known backend facts carried forward:

- **[V]** ollama gemma4 parser leaks `<|tool_call|>`-family tokens into `/v1`
  (ollama#15798, won't-fix); degenerates under streaming multi-tool turns.
  Disqualified for tool use.
- **[V]** Thinking-off is backend-specific — llama.cpp
  `{"chat_template_kwargs":{"enable_thinking":false}}`; ollama
  `{"reasoning_enabled":false,"reasoning_effort":"none"}` (both fields). Expect
  a new concrete value per backend.
- **[V]** llama.cpp `--parallel 1` — default 4 slots each allocate full context
  → 4× KV VRAM.
- **[V]** pi env: `PI_EXTENSION_PATHS`, `PI_REQUEST_PAYLOAD_INJECTION_JSON`,
  `PI_PROVIDER_TRAFFIC_LOG_PATH`, `SEARXNG_BASE_URL`.

## Blocking unknown — fork support

Forking happens at **two independent layers**. Both must work, and they must
agree.

| Layer | Owner | Mechanism | Status |
|---|---|---|---|
| Transcript | pi | `{"type":"new_session","parentSession":<id>}` | **[?]** forks state, or only records lineage? |
| KV cache | llama.cpp | slot/seq save → duplicate → restore | **[?]** see verify list above |

- Requirement: new session inherits base context, base left unmodified.
- Claude equivalent was `--fork-session`. **[V]** there: fork wrote its own
  transcript, base stayed byte-identical.
- pi `docs/rpc.md` not present on this host; `parentSession` has exactly one
  mention in local docs, described only as "fresh session".

**Spike both before any code.**

- Transcript: establish distinctive fact in session A → `new_session` with
  `parentSession: A` → query fact → check A's session file size/mtime.
- Cache: save A's cache → duplicate to B → restore B → confirm B answers from
  A's context without re-prefill → confirm A still restorable.

| Transcript result | Cache result | Design |
|---|---|---|
| Forks | Duplicates | Target design: both layers fork, no re-prefill |
| Lineage only | Duplicates | Cache carries the context; hand pi the parent transcript explicitly. Still no re-prefill. |
| Forks | No duplication | Transcript forks but every branch re-prefills — the O(n²) problem returns. Keep base minimal; reconsider viability. |
| Lineage only | No duplication | Single long-lived session + explicit context editing. Different pattern; decide before building. |

## Architecture — two seams

pi is a harness (agent loop + tools + sessions), not a completion endpoint. Do
not conflate.

| Role | Abstraction | First impl | Needs |
|---|---|---|---|
| Working session | `HarnessInterface` | pi RPC | tools, loop, session, fork |
| Base session | `CompletionInterface` | llama.cpp `/v1` direct | none — receives handoff, replies `acknowledged` |

- Base session bypasses pi entirely: no tools, no agency, one HTTP call.
- Keep `interfaces/` free of pi and llama.cpp specifics. Existing test asserts
  interfaces mention neither harness nor terminal — keep it passing.
- Core loop ports near-unchanged: orchestrator, runner, composer, preamble.

## Removed by RPC

- tmux adapter, `send-keys`, shell-line quoting, pane-readiness detection,
  interrupt-repeat semantics, workspace-trust keypress.
- ~330 adapter lines + readiness layer.

## Open design decision — user surface

- RPC has no TUI. Claude version's working session *was* the user's terminal.
- **[V]** `steer` / `follow_up` exist for mid-run user input.
- Replacement = own UI rendering the event stream + sending commands.
- Decide before porting the loop: it defines what "the session the user works
  in" means.

## Frameworks and packages to evaluate — required research task

Do this survey **before** writing custom implementations. Deliverable: a written
comparison per category, with the adopt/build decision and the reason.

None of the candidate names below are endorsements. They are starting points for
research, listed because they plausibly touch a need. **No claim is made here
about what any of them currently does** — verify against current docs and source.
Add candidates freely; this list is not exhaustive.

| Need | Categories / candidates to research | Decision criteria |
|---|---|---|
| Agent/session orchestration | LangChain, LangGraph, LlamaIndex, Haystack, Semantic Kernel, AutoGen, CrewAI, DSPy, and equivalents | Does it model **forked sessions with divergent history** natively? If it must be adapted around, it is surface without leverage. |
| Explicit state machines | `transitions`, XState-family, statechart libraries, workflow/durable-execution engines (e.g. Temporal-style), actor frameworks | Are the RPC-era states real enough to justify it — streaming, aborting, restoring-cache, context-full, awaiting-user? Do not pick a library before the states are enumerated. |
| Declarative rule engines | JSON/YAML rule DSLs, `json-logic`-style evaluators, policy engines (OPA/Rego-style), decision tables | Can rotation policy be expressed and unit-tested as data? Is the rule set inspectable without reading code? |
| KV cache / prefix reuse | LMCache, vLLM prefix caching + KV connector work, SGLang RadixAttention, llama.cpp state save/load, any cache-offload project | Does it already provide save/restore/**duplicate-into-a-different-sequence**? If so, phase 1 wraps it instead of building it. |
| LLM completion client | provider SDKs, OpenAI-compat clients, LiteLLM-style routers | Thin is better. Only the base-session role needs it. |
| Event stream normalization | streaming JSONL/SSE parsers, schema validators (pydantic-style) | Small enough to hand-write? Prefer a library only if it removes real edge cases. |
| Structured output validation | JSON-schema validators, typed-model libraries, constrained-decoding tooling | Handoff envelope must be validated, not trusted. |
| Process/RPC supervision | subprocess supervisors, async process managers | pi RPC is a long-lived process with a JSONL channel; check for an existing supervisor before writing one. |

Rules for this survey:

- Evaluate against **this** project's needs, not general popularity.
- A dependency that only partly fits, and must be worked around, is worse than a
  small custom tool. Say so explicitly in the comparison when that is the finding.
- Record the survey outcome in the repo. A future reader must be able to see what
  was rejected and why, without redoing the research.

### Rotation policy — the rules to express as data

Regardless of which rule mechanism is chosen:

- rotate on envelope present
- refuse on question-only turn
- refuse a second rotation for one turn
- stop after N rotations with no tool calls ← the bound the predecessor lacked;
  its run had to be killed by hand
- refuse or force rotation based on remaining context budget

## Fixed rules — not up for rediscovery

- Never seed a working session headlessly; its first turn belongs where the user
  can see it.
- Turn ends exactly one of two ways, never both:
  - unfinished → ask, no envelope
  - minimal increment worth saving → envelope, no question
- Emission triggers on minimal increment, not on work complete.
- Working preamble never mentions machinery; `session` is a banned word in it.
- Rotation acts on the envelope, never on a turn merely ending.
- Anything outside the envelope is lost — state this to the agent.
- Verify by measurement; mutation-check guards.
- Spike the mechanism before writing app code around it.
- Exactly one KV cache resident in VRAM. Never trade context budget for
  convenience.
- Restore a cache rather than re-prefill a preamble.
- A branch is a cache and a transcript together, or it is invalid.
- Small discrete tools, each independently testable. No tool knows the
  orchestrator.
- Backend and harness names appear only in their own adapters.
- Adapters declare capabilities; callers degrade. Never fake uniformity across
  backends.
